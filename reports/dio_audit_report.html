4 · Resolved issues (before → applied fix)

P1 · Refresh-token cycle deadlock RESOLVED

Scenario 5 & 10 · auth_interceptor.dart
✅ FIXED
Was

AuthInterceptor extends QueuedInterceptor handled the 401 in onResponse and awaited a refresh on the same Dio; the refresh’s 200 response was stuck behind the original 401 in the one shared _responseQueue, so the request hung forever (verified: refresh fired once, retry never did).

Applied fix — plain Interceptor + throwaway refresh Dio + single-flight Completer
class AuthInterceptor extends Interceptor {              // was: QueuedInterceptor
  ...
  Future<bool> _doRefresh() async {
    final refreshToken = _storage.refreshToken;
    if (refreshToken == null || refreshToken.isEmpty) return false;
    // Throwaway client so the refresh response does NOT pass back through THIS
    // interceptor (routing it through `_dio` re-enters onResponse -> deadlock).
    final tokenDio = Dio(BaseOptions(baseUrl: _dio.options.baseUrl))
      ..httpClientAdapter = _dio.httpClientAdapter;
    final res = await tokenDio.post(
      ApiEndpoints.refreshToken,
      data: {'refresh_token': refreshToken},
      options: Options(validateStatus: (s) => s != null && s < 500),
    );
    if (res.statusCode != 200 || res.data is! Map) return false;
    final data = res.data as Map;
    final access = data['access_token'] ?? data['token'];
    final refresh = data['refresh_token'];
    if (access is! String || access.isEmpty) return false;
    await _storage.save(access: access, refresh: refresh is String ? refresh : null);
    return true;
  }

  /// Single-flight: concurrent 401s all await the same in-flight refresh.
  Future<bool> _refresh() {
    final inFlight = _refreshCompleter;
    if (inFlight != null) return inFlight.future;
    final completer = _refreshCompleter = Completer<bool>();
    _doRefresh()
        .then(completer.complete)
        .catchError((Object e, StackTrace st) => completer.completeError(e, st))
        .whenComplete(() => _refreshCompleter = null);
    return completer.future;
  }

Verified by tests: “401 WITH a refresh token → refresh once then retry” and “concurrent 401s trigger exactly ONE refresh” both pass against the real interceptor.

P2 + P3 · queryParameters TypeError & asFormData dropped RESOLVED

Scenario 7 · base_remote_source.dart
✅ FIXED
Was

_normalizeArabicDigits returned a Map<dynamic, Object?>. That made the queryParameters … as Map<String, dynamic> cast throw an uncaught TypeError (crashing every list/search GET), and made the asFormData && requestData is Map<String, dynamic> guard fail (so uploads were sent as broken JSON, never as multipart).

Applied fix — preserve the Map<String, dynamic> shape
static Object? _normalizeArabicDigits(Object? value) {
  if (value is String) return value.toEnglishNumbers();
  if (value is Map) {
    // Keep the result a Map<String, dynamic> (and stringify keys) so the
    // `as Map<String, dynamic>` cast on queryParameters and the
    // `requestData is Map<String, dynamic>` asFormData guard both still hold.
    return value.map<String, dynamic>(
      (k, v) => MapEntry(k.toString(), _normalizeArabicDigits(v)),
    );
  }
  if (value is List) {
    return value.map(_normalizeArabicDigits).toList();
  }
  return value;
}

Verified: “queryParameters reaches the network” (query intact) and “request(asFormData:true) sends a multipart body” (multipart/form-data; boundary=…) both pass.

P4 · Non-JSON body misclassified as “no internet” RESOLVED

Scenario 4 & 3 · response_parser.dart
✅ FIXED
Was

A WAF/Cloudflare HTML page or a truncated body served with Content-Type: application/json made Dio’s transformer throw a FormatException → DioException(unknown) → mapped to NetworkFailure, hiding the real error behind a false “no internet.”

Applied fix — classify the decode failure as a parse error
// in parseDioError's switch:
DioExceptionType.connectionError => _classifyConnectionError(e),
DioExceptionType.unknown => _classifyUnknown(e),          // split out

/// A json-decode FormatException (HTML/garbage/truncated body under a JSON
/// content-type) becomes a ParseFailure, not a misleading "no internet".
/// A genuine transport problem (SocketException) stays a network failure.
static AppException _classifyUnknown(DioException e) {
  final inner = e.error;
  if (inner is SocketException) return NetworkException(inner.message);
  if (inner is FormatException) return const HtmlResponseException();
  if (_looksLikeHtml(e.response?.data)) return const HtmlResponseException();
  return NetworkException(e.message);
}

Verified: “HTML mislabelled as application/json → ParseFailure” and “malformed JSON → ParseFailure” both pass; the existing text/html cases still pass.

P5 · Retried multipart reused single-use FormData RESOLVED

Scenario 7 · auth_interceptor.dart
✅ FIXED
Was

_retry re-issued the same RequestOptions whose FormData was already finalised; re-reading it throws StateError, which the catch turned into a token-clearing logout — losing the upload and the freshly-refreshed session.

Applied fix — clone the single-use body before replay
Future<Response<dynamic>> _retry(RequestOptions req) {
  req.extra[_retriedFlag] = true;
  req.headers['Authorization'] = 'Bearer ${_storage.accessToken}';
  // FormData is single-use; clone so the retried multipart body is rebuilt
  // instead of throwing a StateError (which would silently log the user out).
  final data = req.data;
  if (data is FormData) {
    req.data = data.clone();
  }
  return _dio.fetch(req);
}

Verified: “a 401’d multipart upload is retried with a rebuilt, non-empty body” drives the real request(asFormData) → 401 → refresh → retry path and asserts the retry body length > 0.

P6 · Offline replay had no idempotency key RESOLVED

Scenario 9 · offline_queue_manager.dart
✅ FIXED
Was

Queued POST/PUT/PATCH/DELETE were replayed with no idempotency key; a reply lost after the server committed would be re-sent, creating a duplicate (double charge / double sign-up).

Applied fix — stamp the op’s stable UUID as an Idempotency-Key
Future<void> _runOne(QueuedOperation op) async {
  // Stable across every retry of THIS op (op.id is a v4 UUID set at enqueue);
  // a server that honours Idempotency-Key collapses the retried write.
  final headers = <String, dynamic>{
    ...?op.headers,
    'Idempotency-Key': op.id,
  };
  try {
    final res = await _dio.request<dynamic>(
      op.endpoint,
      data: op.body,
      options: Options(method: op.method, headers: headers),
    );
    ...
  }
}

Verified: “replayed non-idempotent op carries a stable Idempotency-Key” asserts the replay header equals op.id. (Requires a server that honours Idempotency-Key — the standard pattern.) With P1 fixed, a 401 during replay now refreshes cleanly instead of hanging the sync loop.
